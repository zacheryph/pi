Roadmap · supersedes PR #207

Pi Attention Queue

One place that answers “what needs me?”, for one session and for all of them. PR review handoffs are the first source, and the contract leaves room for more.

Chosen · 26 Nov 2026 · mockups are drawn by hand, not captured

Two kinds of attention

PR #207 treats a review handoff as a Git feature. To make it generic, split “needs you” by whether the agent can keep going.

Blocking

The agent has stopped and cannot continue until you act.

  • An open ask questionnaire
  • Pi waiting on a dialog (status waiting)
Already in every snapshot. Consumers derive these; no producer changes.

Owed

The agent handed something off and moved on. It waits on you outside the session.

  • A draft PR handed to you for review
  • Later: unreviewed todo findings, a failed check you own
New: an extension publishes it as an attention view, and it lasts after Pi stops.

The context card shows a thread's Owed items. bb's composer already takes over for a Blocking question, so repeating it in the card adds noise. The Attention page shows both kinds across every session, with Blocking first.

1. A new pi-surface view kind: attention

An explorer could carry these rows, but settling strips its actions and the bb card would have to scrape links from detail fields again (PR #207 makes the same point). A small dedicated kind gives every consumer typed rows: state, timestamps and a link that still works with no process. Consumers that don't know the kind skip it, as they do today. 

// packages/pi-surface/src/attention.ts
export interface AttentionItem {
  id: string;            // stable within the view: "pr:github.com/acme/web#42"
  rev?: string;          // what was handed off (head SHA); a dismissal names it
  category: string;      // "review" | "findings" | …; a renderer maps it to an icon, unknown → generic
  title: Line;           // "Review acme/web#42"
  reason?: string;       // "Checkout cleanup · draft at a13c90e" (bounded)
  state: "ready" | "stale";
  since: number;         // when it was raised
  observedAt?: number;   // when the producer last confirmed it
  link?: { url: string; label: string };  // https only; checked again by every consumer
  open?: ActionRef;      // optional in-session action (e.g. open /todo:review); live only
  dismiss?: ActionRef;   // live only
  live?: true;           // exists only while the process runs: settling removes the item
}
export interface AttentionModel { items: AttentionItem[]; total: number }
Rule What it means
Settling Items marked live are removed; open and dismiss are dropped. Everything else, the link included, survives as last known.
Bounds MAX_ATTENTION_ITEMS (around 50), bounded title and reason, as isFormModel enforces for forms. total stays the producer's true count, so a capped list can say “and 12 more”.
Ids Views are <extension>.attention. Across sessions an item's key is threadId / viewId / itemId.
No inference A producer raises an item only on an explicit event, such as a handoff tool call or a recorded finding. Consumers never invent Owed items.

2. Producers own their items

Each producer follows the runtime rules already in place: state lives in the factory closure, is written with pi.appendEntry, rebuilt with readEntries on session_start and session_tree, published with views.define and views.changed. No producer needs to know about bb, the dashboard or the page.

pi-git, first producer. Reuse #207's reducer (steps 1–2) and add git_pr_request_review (main session only). It checks that the PR is open and that its head is the SHA given, records a git:attention entry and arms a watch. The watch is a pi-work item, so the session wakes when the PR changes and the item moves on without anything polling.

For a draft handed off for review, resolved means a later observation shows draft: false, an approving review, a merge or a close. These are the fields pi-git already reads (draft, review, state, headSha). A checks-only update never resolves an item.

pi-todo, second producer (later). A task with unreviewed messages becomes one findings item, with an open action to its review. It has no link, so in bb the row opens the thread. If it fits the contract without changes, the contract is generic enough.

Decisions

All four were decided on 26 Nov 2026 as recommended.

Decided: derive

Questions are derived, not published by pi-ask

Blocking rows come from form views and session status. No producer changes and no duplicated state. Reconsider only if a Blocking source appears that no existing view covers.

Decided: per-domain tools first

Only domain tools raise Owed items

Domain tools such as git_pr_request_review can validate their input and resolve their own items. A generic tool waits; see below.

Decided: separate page

Attention is its own page in bb's sidebar

It has its own badge and URL. The Pi sessions badge moves to it, so the sidebar shows one count.

Decided: dashboard

The dashboard is the cross-session view for terminal users

/attention stays per-session. There is no cross-session index in the terminal.

Later: a generic attention_raise tool

Not in this plan. Some handoffs will have no domain tool: “check the staging deploy”, “approve the migration in the console”. When a real case like that comes up, a generic tool can raise an Owed item with the same contract. To keep it from becoming a noisy inbox, it would have these limits:

  • Main session only, like user_notify. A subagent reports to its parent.
  • Required expiry. Nothing can observe a generic item resolving, so it needs a deadline (say 1–72 hours) and shows as stale once that passes.
  • Link optional and checked. https only, with no userinfo, checked again by every consumer.
  • Dedupe by key. Raising the same key again updates the item instead of adding another.
  • A cap. A few open generic items per session at most; past that the tool refuses.
  • Resolved by you or the agent. Dismiss in any UI, or attention_resolve(key) once the agent sees it is done.

It would live in the pi-attention extension and publish attention.items with category agent. The contract needs no change.

Preparation lands first: contract, then consumers drawn from fixtures, then the producer. The last step turns real handoffs on. Each step ships alone and updates its own READMEs and images.
